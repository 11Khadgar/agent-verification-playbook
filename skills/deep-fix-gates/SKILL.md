## When to Use
用户要在开源仓库提 issue、提 PR、报 bug、解释「为什么我的修复被拒」时。也适用于本地修复一个自称"偶发"的 bug、或任何要写补丁给别人 review 的场合。不适用于纯本地一次性脚本。

## Procedure
1. 拆三层：把 bug 写成三栏表 —— 成因（机制，为什么坏）/ 触发条件（在什么输入或时序下坏）/ 症状（用户看到什么）。修复必须挂在「症状」上。挂在触发条件上 = 只治一种坏法。例：成因是 Chrome 在 paste 中途重读剪贴板、触发是纯文本粘贴、症状是「粘贴后没 input 事件、值没变」。挂在症状上才通用。
2. 覆盖面扫描：grep 出所有走同一处理路径的分支和调用方（同一个 handler、同一个事件类型、同一个 helper），逐个标 ✅受影响 / ❌不受影响 / ❓未知。只要有 ❓ 就还没分析完。原方案用 if (!html) 把 ❓ 当 ❌ 处理了，富文本粘贴当场漏掉。
3. 成本基准：测量「正常路径」，不是「坏的那次」。99% 的操作走正常路径，任何让正常路径变慢的修复都要先出数字再提交。用最小独立 repro 页 + console.time，给数量级而非个位数：10 行 / 1000 行 / 4000 行 / 1MB 各一次。作者的 4000 行 13.6 s vs 原生 28 ms 是让方案存活/死亡的那一个数字。
4. 换预测为观测：不要问「我猜这里会坏」，要问「有什么可观测事实能区分坏和没坏」。可观测事实的例子：有没有 input 事件、DOM 有没有变、返回是不是空、值是不是没变。可观测判据在换浏览器 / 换版本 / 换剪贴板格式后仍然有效，预测判据会静默失效（而且失效方式是「不粘了」，比慢更难被发现）。
5. 砍 diff 并设计回滚：目标 20 行以内、单文件、状态只加一处，且能被既有信号清掉（作者让 handleInput 清 ref）。如果需要新状态机、新配置、新抽象层，说明还没找到最小着力点，回第 4 步重找判据。行数和文件数超过同行方案 3 倍就是砍得不够。
6. 写下不变量并作为 issue 的第一段：在 docs/ 或代码注释留一句「永远不要 X，因为 Y（带数字）」。否则下一个人会把你的坑再踩一遍。提交措辞同理：先给根因证据，再给否掉某方案的数字，最后才是补丁；不要把「我准备好 PR 了」放开头，那是要人情，不是要评审。

## Pitfalls
- 把「我的场景」当「全部场景」：只验某个 TTS 项目的 20 字短句就宣布通用，等于把 20 字样本推广到 1 MB。任何性能或正确性结论都必须带规模。
- 补丁越完整越难被接受：4 文件 +119 行 + e2e + 已部署 会被维护者当成横切改造，18 行 + 一条文档才会被当成修 bug。e2e 留给自己，不塞进首轮 PR。
- 「我的根因分析是对的」和「我的修复是对的」是两件事，别混为一谈去争。作者否掉的通常只是作用域，不是你的诊断——先分辨他否的是哪一件。
- preventDefault 是有代价的：一旦接管原生行为，就同时接管了所有你没想到的原生细节（拼写检查、IME、无障碍、输入法、粘贴后的滚动）。只为了修一个偶发，不值得全局接管。
- 捕获的时刻 vs 消费的时刻：延时/异步补救一定存在「记下的选区、DOM 引用在消费时已经过期」的窗口。必须加三重收窄：对象身份对比（防并发覆盖）、isConnected（防节点已卸载）、defaultPrevented（防和别人打架）。
- 不要在还没量出数字的时候就替用户决定「这个性能不重要」。改动的成本必须被测过，不能靠直觉。

## Verification
1. 6 格表能填满、且没有 ❓：成因 / 触发 / 症状 / 受影响分支 / 正常路径成本 / 最小判据。
2. 能回答这句话：「如果维护者说不按我的改，我的东西里哪一部分还能站住？」——能站住的是根因分析，其余是偏好。
3. 提交前统计 diff：文件数 ≤ 2，净增行数 ≤ 30，且没有新增抽象层/状态机/配置项（否则回到第 5 步）。
4. 数字齐全：至少一组「坏路径耗时 vs 正常路径耗时」，同规模对比。
