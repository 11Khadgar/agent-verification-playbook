## When to Use
适用于：仓库中交付一个跨多个模块/文件的功能或重构，工作确实可切分并行，用户要求分角色、开团队或按团队提示词流程执行；也适用于用户明确要「任务清单+依赖+所有权+独立审查」这类交付物。

不适用于：单文件或 ≤2 个文件的改动、模块间强依赖必须先串行的实现、纯调研问答（走只读子代理）、用户没有要求并行编排却要开编排器。

与并行执行层分工：本 skill 只管拆分/角色/契约/闸门/报告；worktree 源码副本隔离、具体并发原语与独立分支验收细节属执行层实现，某个 harness 的对照示例见附录 A，不在此重复。

## Procedure
1. 先读仓库再动手：用只读子代理或 read/grep 摸清结构，产出一张模块表、一份接口/数据形状契约（逐字，不给形容词）、一条真能跑的验收命令。契约不统一就开工，必然出现各自单测通过而集成失败。
2. 过闸门再组队：自包含可交付模块 ≥3 个才组 3-5 名成员；少于 3 个直接改。角色只按职能分四类——架构（只读，产出模块划分与契约）、实现（owner 自己的路径）、测试（写测试并跑验收命令）、审查（只读）；前端/后端只是实现角色的两个 owner，不按人数编角色。
3. 画文件所有权图（表格：路径 glob → owner），一行一路径，禁止交叉。共享文件（package.json、schema、barrel export、迁移文件）指定唯一 owner 且最先落地。
4. 拆任务：每人 5-6 条以内、自包含、可交付，写明依赖（blockedBy），并规定阻塞解除后由谁认领。任务名短、可判定完成。
5. 给每个成员写 spawn prompt，六要素一条不缺：姓名-角色 / 目标+该功能对使用者的价值 / 可编辑文件与目录（完整路径）与禁改区 / 技术栈·约定·接口·已定决策（子代理不继承父会话，必须内联）/ 可证明完成的测试或检查命令 / 向谁汇报什么、与谁直接对接接口问题。
6. 执行：子代理独立任务用编排器提供的并发原语并发，有依赖的分阶段；具体调用形式随 harness 不同，示例见附录 A。给机器可读结果时用结构化输出约定（如 JSON Schema）。需多智能体编排时才启用编排器，其余情况本地直接改。
7. 主代理只协调不实现，介入只有三种触发：偏航、缺上下文、接口冲突。介入方式是直接补上下文或改 prompt，不是再 spawn 一层。仅在不可逆操作、销毁重建、明确变更范围时暂停确认。
8. 审查独立：审查员只读、新上下文、只看 spec + diff，不继承实现者的自我评价，也不许改文件。让实现者与测试者直接对接解决接口问题。
9. 闸门：验收命令真实跑通才标记完成。失败就照原样贴输出，不降级断言、不跳过测试、不把「已提交 diff」当完成。
10. 交付：成员名单 + 文件所有权图 + 带依赖的任务清单 + 完成声明核对表（每条声明 → 执行的命令 → 输出摘要，真实复跑一次）+ 未验证项 + 下一步。报告面向没看过过程的读者，先给结果，再写改动、未验证项、下一步。收尾清理本轮临时产物与已确认的测试会话。

## Pitfalls
- 附录 A 里那些调用形式是某一个 harness 的契约，不是通用标准：换 harness 前先核对它是否支持并发原语、是否支持按成员指定模型、结果 schema 怎么传。做不到就降级成串行 + 人工复核，不要假装指定了。
- 不要引用不存在的角色定义目录（例如某些 harness 约定 `.claude/agents/`，先确认它真的存在）。角色要么内联进 spawn prompt，要么落成 skill。
- 子代理看不到父会话上下文：六要素里漏掉路径、接口形状或已定决策，就会出现两个 agent 各写一套数据类型、各自单测通过、集成崩掉。验收断言不放宽。
- parallel() 传 promise 数组会报错，必须 map 成 thunk；漏检返回 null 的失败分支，会把失败当成功写进汇总报告。
- workflow 脚本必须 export const meta 且至少调用一次 agent()，只声明 phase 会被拒；脚本内禁 Date.now / Math.random / new Date，需要「今天」由调用方通过 args 传入。
- 不要为概念上的团队叠框架：别再自造依赖 DAG、持久恢复、自动合并系统。先由主 agent 拆任务和验收。
- 「负责人只协调」不等于甩手：缺上下文或偏航时主代理必须直接介入补，最贵的失败是团队在没有契约的情况下跑完全程。
- 协调成本是真的：少于 3 个可并行模块、或单文件修复时，团队模式比直接改更慢更贵，还容易碎片化上下文。此时明确说「这个不值得组队」并按直接改走。

## Verification
1. 验收命令在最终集成树上真实跑通，输出被保留进报告；没有删除、跳过或放宽任何测试来制造通过。
2. 对 diff 做一次所有权核查：不存在两名 owner 交叉修改同一文件；共享文件只由指定 owner 改过。
3. 每条完成声明都能对上一条具体命令和输出；对不上的降级为未验证并写进报告。
4. 未完成、失败、未验证项在报告里显式列出，附原始输出，不用「基本完成」含糊掉。
5. 项目内无残留临时 worktree / 分支 / 日志；测试用的 agent 会话已按需关闭持久化并清理，磁盘删除不被当作会话已清除。

## 附录 A：执行层对照（Pi coding agent，2026-11 快照）

以下只是某一 harness 的具体写法，用于说明「并发原语 + 结构化输出」长什么样；契约会变，换 harness 请重新核对，不要把这段当标准。

- 并发：`parallel()` 收 thunk 而不是 promise，`await parallel(items.map(i => () => agent(prompt, { label: '唯一短标签' })))`；有依赖的场景用 `pipeline(items, ...stages)`。
- 结构化结果：`agent()` 支持传 JSON Schema 校验返回值；失败分支返回 null，必须显式检查，否则会把失败当成功写进汇总。
- 编排脚本约束：必须 `export const meta = { name, description }` 且至少调用一次 `agent()`；脚本内禁用 `Date.now` / `Math.random` / `new Date`，需要「今天」由调用方通过 args 传入。
- 模型选择：该 harness 的 `agent()` 只接受 label / schema，没有 model 入参，按成员指定模型做不到，模型跟随项目/全局配置。
- 执行隔离：源码副本隔离（worktree / 独立 clone）与分支验收细节属执行层，不在本 skill 范围。
