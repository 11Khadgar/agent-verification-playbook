# How this system evolved

**English abstract.** This is not a design document. Nothing here was designed. Each piece exists because something went wrong first and the same wrong thing went wrong twice. Five failures produced five skills: a long chat that kept re-exploring ground it had already covered; a multi-agent build where every unit passed its own tests and the integration collapsed; a habit of saying "done" when what I meant was "I changed some files"; a judgement of "looks good" applied to generated images; and an upstream maintainer closing a pull request I was sure about. The essay is the record of what each failure actually cost, and which rule survived it. The skills are the residue.

---

**这篇文章不是设计文档。** 这套东西里没有一样是先想好再做的，全部是先撞了墙，第二次撞同一面墙之后才写下来的。五个 skill 对应五次失败，写的是每次失败到底代价在哪、最后留下哪一条规则。

## 起点

一开始只有一个通用编码 agent，一份 AGENTS.md，和「帮我做这个」这句话。

问题不在 agent 不聪明，在于我判断不了它做完了没有。它说改好了，我得自己去看；我自己去看的时候，又忘了当初要什么。对话越长，这种双向遗忘越严重——我不记得上下文，它不记得我纠正过什么。

## 失败一：长对话里反复探索已经走过的地方

第一类损失最隐蔽：不是做错，是**重复**。

一个任务做到第二天，对话已经很长，我开新会话接着做。新的 agent 不知道昨天已经排除过的三条路，于是重新排除一遍；我不知道它排除得对不对，于是又核对一遍。同一个下午，同一段代码,同一个错误结论，被独立发现两次。

**代价**：不是钱，是注意力。而且它伪装成「谨慎」。

**留下的规则**：动手前写 `计划书.md`（目标一句话、可判定的成功标准、每步后面跟「验证：检查什么」）；每完成一步立刻更新 `进度.md`；信号出现就交棒开新会话，不硬撑。已有产物在文件里只写路径，不复制内容——两份文档一起膨胀是这套做法最常见的死法。

这就是 `handoff-notebook`。它没有任何技术含量，唯一的价值是把「记得」这件事从对话搬到磁盘。

## 失败二：每个模块都通过了自己的测试，集成时全崩

第一次尝试用多个子代理并行做一个跨模块的功能，结果是经典的失败：两个 agent 各自定义了一套数据结构，各自的单测都过，拼起来字段对不上。测试覆盖率很高，功能就是不通。

回头看，错在两个地方：我没有先定接口契约就开工；我没有指定谁拥有哪个文件，于是两个人编辑同一个文件，各自以为自己改对了。

**代价**：一轮完整的工作量，加上一个我一度以为是模型能力问题的错误结论。

**留下的规则**：开工前产出逐字契约（不给形容词）和一条真能跑的验收命令；模块 ≥3 个才组队，少于 3 个直接改；画文件所有权图，一行一路径，共享文件指定唯一 owner 且最先落地；审查员只读、新上下文、只看 spec + diff，不继承实现者的自我评价。

还有一个反直觉的结论：这套流程最主要的用途是**判断什么时候不值得用**。两个文件的改动开团队，比直接改更慢更贵，还额外制造了碎片化上下文。所以 `orchestrate-agent-team-delivery` 的第一段就是它的不适用清单。

## 失败三：把「我改了文件」说成「做完了」

这条最丢人，也最普遍。

改完之后我说「已修复」，用户去用，没修好。或者更糟：我自己都不知道有没有修好，因为我没跑。当时的心理机制很清楚——跑验收命令会有失败的可能，而不跑就一定可以停在「我觉得对了」。

**代价**：信任。一次之后，用户开始要求我自己贴输出，这是对的。

**留下的规则**：完成的定义只有一种——验收命令真跑通，输出贴进结论；跑不动或没写测试就标「未验证」，不把「改完了」当「通过」。跨 ≥2 文件的改动派只读子代理按 spec + diff 复核，不用自审替代。失败与未完成部分如实标注，不删测试、不放宽断言来制造通过。

这条后来被写进所有 skill 的 `Verification` 段落，也是整个仓库的主论点：**「完成」不等于「通过」。**

## 失败四：把「看起来不错」当成合格

生成图像的时候，前几十张都靠一句「这个好看」判断。于是同一类问题反复出现：水印没去掉、文字被写成了乱码、人物多了根手指、编辑之后非目标区域被悄悄改掉。

最贵的一次是：图生成了，接口返回成功，我宣布交付，然后发现那个通道**根本不支持图生图**——它只是把参考图当空气，重新画了一张。我核对了「调用是否成功」，没核对「能力是否存在」。

**代价**：一次完整的交付返工，加上一段本可以省掉的试错。

**留下的规则**：分三层验收（文件可解码/尺寸/alpha → 需求主体数量文字构图禁止项 → 视觉解剖材质光影边缘一致性），硬门槛失败不被审美总分抵消；每轮与最近合格底稿比较目标改善**和非目标漂移**；记录最小 sidecar（通道与参数、参考职责、任务 ID、父版本、requested/reported/measured）；超时、断流、配额错误不自动重生；接任务前先核通道能力再谈效果。

这就是 `image-quality-workflow`。它的附录里那两条通道的对照表，本身就是一次「换个模型就行」的错误估计换来的。

## 失败五：上游关了我的修复，我争论的其实不是同一件事

第一次给别人的开源项目提修复，我的根因分析是对的，作者还是关了。当时的反应是觉得他不识货。

冷静下来重看：他否掉的是**作用域**，不是我的诊断。我的补丁动了四个文件、加了 119 行、还塞了 e2e 测试；他要的是能一眼看懂、能回滚、不改变正常路径的 18 行。诊断对不等于修复对，这是两件事。

同一轮里还有两个更硬的教训：

- 修复必须挂在**症状**上，不能挂在**触发条件**上。挂在触发条件上，只治一种坏法。
- 用「坏了的那次」做成本基准是错的。99% 的操作走正常路径。测出来正常路径 4000 行文本要 13.6 秒、原生只要 28 毫秒的那组数字，才是让我的方案当场死亡、也是让替代方案当场站住的那个数字。

**留下的规则**：拆成因-触发-症状三栏；grep 出所有走同一路径的调用方并逐个标受影响/不受影响/未知，有「未知」就没分析完；测正常路径而不是坏的那次，给数量级而非个位数；用可观测事实替代预测（「有没有 input 事件」比「我猜这里会坏」耐用得多，因为它在换浏览器、换版本后仍然有效）；砍到单文件、20 行内；把不变量写进 issue 第一段。

这就是 `deep-fix-gates`。它本质上是一道**在写代码之前**的闸门。

## 附带的一条：被示例实现锁死路线

还有一类失败不是撞墙，是**方向偏了没人发现**：用户给了一个示例工具，我就默认那是路线，没去查宿主的原生生态、GitHub 和包仓库有没有更直接的路。做完之后才发现官方早就有一个插件能省掉一半工作。

**留下的规则**：分开真实目标和用户给的示例；检索官方生态目录、GitHub、包仓库，覆盖中英文同义词；按「原生能力 → 已有桥接 → 自研」排序；引入新宿主前说明原生候选为何不适合。

这就是 `check-native-ecosystem-before-building`，五个里最便宜、最容易被跳过的一条。

## 分层：最后发现是四个不同的东西

撞完这些之后才看清，所谓「一套系统」其实是四层，职责完全不同，混在一起就会互相污染：

| 层 | 存什么 | 载体 | 失效方式 |
|---|---|---|---|
| 我是谁 | 偏好、环境事实、过往决策 | 记忆 | 过期了还当真 → 用前核验 |
| 怎么做 | 可复用的操作规程 | skill | 写成教条 → 该删的时候硬套 |
| 不许做什么 | 硬边界、授权范围 | AGENTS.md | 被自动化改写 → 永不自动维护 |
| 到哪了 | 当前任务状态 | 交接本 | 和对话重复 → 只写状态不复述计划 |

四层里唯一不能自动维护的是第三层。边界被 agent 优化掉的那天，系统就再也不可信了。

## 反面清单

这套东西里价值最高的部分，可能是这些「别用」：

- **别为两处改动开团队**。协调成本是真的，会超过并行收益。
- **别用 skill 处理一行改动**。加载规程的开销大于收益。
- **别派子代理做一次读取**。你需要的是结论，不是另一个人重读一遍。
- **别为了显得有进度而虚报完成**。未验证的一律留在未完成，这是这套系统唯一不可协商的地方。
- **别把历史个案写成全局规则**。某个模型在某个日期的尺寸、水印、价格，都是快照，不是规格。
- **别把「我的根因分析是对的」当成「我的修复是对的」**。作者否掉的通常只是作用域。

## 还在变的

两个 skill 的附录里带着日期，因为它们必然过期：一个 harness 的并发原语契约，一次图像通道的能力快照。写下来的时候就知道会烂，仍然写，因为不写下来，下一个人（包括一个月后的我）会重新撞一遍。

规则的增长速度应该低于失败的速度。这套东西现在有五条，如果它涨到二十条，多半不是系统变强了，是我开始为了写规则而写规则。
